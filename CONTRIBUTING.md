# Contributing

Thanks for being here. This site is built by neighbors, and help is genuinely welcome.

One thing to know up front, because it shapes everything below: **people rely on this
site during wildfires.** A bug on the fire page isn't a cosmetic problem, it's someone
getting the wrong answer to "do we need to leave?" That's why a few rules below are
firmer than you'd expect for a small community site.

## How to contribute

**You don't need any special access.** Fork the repo, make your change, open a pull
request. That's it.

1. Fork this repo (button in the top right on GitHub)
2. Make your change
3. Open a pull request describing what you changed and why
4. It gets reviewed and merged

Merging deploys to the live site within about a minute, so review is deliberate.

## Running it locally

No build step, no npm install, no framework. You need Node installed, then:

```
node server.js
```

Open http://localhost:3100. That's the whole setup.

**What won't work locally:** anything under `api/` (those are Vercel serverless
functions, so `/api/calfire` returns 404 locally). The page handles that gracefully,
but it means CAL FIRE acreage and containment won't appear until deployed. If you're
changing anything that depends on that data, verify it on the live site after merge.

There are no tests. Verification is: load the page, open the browser console, confirm
no errors, and check the thing you changed actually behaves.

## Good first contributions

- Fixing wrong or outdated local info on **Living Here** (phone numbers, hours, links)
- Adding a local business or resource neighbors have recommended
- Typos, clearer wording, broken links anywhere
- Adding events to `community-events.json` (neighborhood events, not the auto-fed ones)
- Accessibility improvements

## Please check with the owner first

These are load-bearing, and a well-meaning change can break them in ways that aren't
visible until a real emergency:

- `scripts/alert-watch.mjs` — decides what triggers a neighborhood alert
- The evacuation, fire-distance, or air-quality logic in `fire.html` / `nav.js`
- Anything in `.github/workflows/`
- `api/` — the serverless functions

## The rules that aren't obvious

These exist because each one was a real bug at some point.

**A failed feed is "unknown", never "all clear."**
If a data source doesn't load, the page must say so. It must never render silence as
good news. Look at how `live.ok` is used in `fire.html` — every feed tracks whether it
actually loaded, and the hero refuses to show a green all-clear unless every check
succeeded. Preserve that.

**Evacuation and fire logic exists in three places and must stay in lockstep.**
`nav.js` (the site-wide status strip), `fire.html` (the dashboard), and
`scripts/alert-watch.mjs` (the alert bot) each compute this independently. If you
change how a fire is selected, how far counts as "near us," or how an evacuation zone
is matched, change all three. They disagreeing is a bug that has bitten this project
more than once.

**Escape everything from an external feed before it touches `innerHTML`.**
Fire names, alert headlines, event titles, and Cal OES notes all come from feeds we
don't control. Use the existing `esc()` / `escT()` helpers. Links get gated too — only
`http(s)` URLs are allowed through to an `href`.

**Never echo Cal OES `NOTES` verbatim.**
That field sometimes contains an entire county alert ("LEAVE NOW. Your safety is in
danger..."). Run it through `briefNote()`, which keeps short notes and reduces long
ones to just the fire name.

**Distances and alarm thresholds are tuned, not arbitrary.**
The mileage cutoffs and acreage tiers were calibrated deliberately so the site informs
without crying wolf. Distances are straight-line and are labeled as such, because
straight-line reads shorter than driving miles. If a threshold seems wrong, that's a
conversation, not a quick edit.

**Alert wording is deterministic templates, never AI-generated.**
The Friday events roundup uses AI. Safety alerts never do.

**Don't hand-edit bot-written files.**
`events.json`, `ai-events.json`, `roads.json`, `alert.json`, and `roundup.json` are
generated by scheduled jobs. Your edits will be overwritten. `community-events.json`
is the one that *is* maintained by hand.

**Bump the nav cache version when you change `nav.js`.**
It's loaded as `/nav.js?v=N` on all six pages. If you change its behavior, increment
`N` everywhere and bump `CACHE_KEY` inside the file to match, otherwise browsers keep
running the old copy for up to five minutes and cached status text lingers.

**Don't add CDN dependencies.**
Leaflet is vendored locally on purpose. During an emergency the network is the least
reliable thing in the picture, so the site shouldn't depend on someone else's server.

**Never slice a string containing emoji by character count.**
Compound emoji (like 🧑‍🌾) span multiple units, and cutting one in half produces
invalid text that crashes URL encoding. Use `[...str]` to work in code points.

## Editorial guidelines

- **Nothing invented.** Every fact links to or comes from an official source.
- **The site is unofficial.** It's not the HOA and not an emergency service. Copy
  should never imply otherwise.
- **No board meeting schedules or internal HOA matters.** Neighbors asked for this
  specifically; the HOA page covers public California law only.
- **No raw WhatsApp group invite links.** Groups are listed with "ask an admin to add
  you" so bots and non-residents can't wander in.
- **No personal information about neighbors**, including the site's maintainer. The
  site describes itself as "a neighbor project."
- **Plain language.** The audience includes people in their 70s reading on a phone
  during a smoke event. Avoid jargon; spell things out.

## Reporting something wrong

If you spot bad information on the site, that's the most valuable thing you can report.
Open an issue, or mention it in the community group chat if that's easier.
